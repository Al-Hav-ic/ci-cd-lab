01Навіщо проєктувати до коду

Раннє проєктування зменшує вартість змін: помилку у вимогах дешевше виправити в тексті Use Case, ніж переписувати міграції, API та тести. UML не замінює код, але задає <strong>спільну мову</strong> між аналітиком, розробником і замовником.

У курсі лаб. 2 — міст між CI/CD (лаб. 1) і PHP/Laravel (лаб. 3–5): те, що ви опишете в <code>docs/architecture.md</code>, далі проявиться в масивах <code>Product</code>, класах <code>App\Models\Product</code> і <code>ProductController</code>.

Предметна галузь — множина понять і правил реального світу (товар, замовлення, оплата), які система відображає в даних і алгоритмах.

Мінімальний набір для звіту та <code>architecture.md</code>:

ЕлементМінімумПриклад (інтернет-магазин)
Призначення1 абзацпродаж через веб-вітрину з оплатою та доставкою
Функції≥5 дієслівшукати, додавати в кошик, оформлювати, оплачувати, звітувати

Паспорт системи — таблиця з цими параметрами; вона копіюється в звіт і в розділ 1 docs/architecture.md.

03Актори та межі системи

Актор — роль (людина або зовнішня система), яка ініціює дії з системою. Актор не є частиною коду магазину: платіжний шлюз — окремий сервіс, але на Use Case діаграмі він потрібен, бо UC «Оплатити замовлення» без нього не завершується. Межі системи фіксують, що входить у scope, а що ні. Наприклад: магазин передає адресу перевізнику, але не будує маршрути доставки — це поза системою.

04Архітектура MVC і Laravel

MVC (Model–View–Controller) розділяє відповідальності:
ШарРольLaravel
Modelдані, правила, зв'язкиEloquent-моделі (Product, Order)
Viewпредставлення для користувачаBlade-шаблони
ControllerHTTP-запит → дія → відповідьProductController, OrderController

Додатково виділяють <strong>Service</strong> для складної логіки (оплата, знижки), щоб контролер не перетворювався на «товстий» клас.

Потік: <code>Route</code> → <code>Middleware</code> → <code>Controller</code> → <code>Model</code>/<code>Service</code> → <code>View</code> або JSON.

05Use Case: три форми опису

Use Case (UC) — цілісний сценарій досягнення мети актором («Оформити замовлення»), а не один клік.
ФормаОбсягКоли використовувати
Коротка1 абзацогляд для замовника
Поверхневаголовний + 3–5 альтернатившвидке узгодження
Повнатаблиця з pre/postconditions, ≥10 кроків, ≥5 extensionsметодичка, захист
Головний сценарій — «щасливий шлях». Extensions — відгалуження (3a, 11b): помилка оплати, timeout шлюзу, невалідна адреса.

Use Case ≠ окремий HTTP-запит: один UC «Оформити замовлення» включає багато кроків UI і викликів API.

06Діаграма варіантів використання

Елементи: <strong>актори</strong> (stick figure), <strong>use cases</strong> (еліпси), <strong>межа системи</strong> (прямокутник).

Типи зв&#039;язків (усі чотири обов&#039;язкові на діаграмі лаб. 2):

Зв'язокUMLСенсПриклад
Асоціаціясуцільна лініяактор ініціює UCПокупець → «Переглянути каталог»
Include<<include>>базовий UC завжди викликає інший«Оформити замовлення» include «Оплатити»
Extend<<extend>>розширення за умови«Промокод» extend «Знижка»
Generalizationстрілка з порожнім трикутником«є видом»Admin → Manager → Customer
Include vs extend: include — обов'язкова частина; extend — опційна поведінка в точці розширення базового UC.

07Діаграма класів

Діаграма класів описує статичну структуру: класи, атрибути, операції, відношення.

Вимоги лаб. 2: ≥10 класів; у кожного ≥5 атрибутів і ≥5 операцій <strong>з типами</strong>; назви класів англійською в <strong>однині</strong> (<code>Product</code>, не <code>Products</code>).

Чотири типи відношень:

ТипПозначенняСемантикаПриклад
Наслідування`-->`is-aCustomer → User
Асоціація--знає один одногоCustomer — Order
Агрегаціяo--частина може жити окремоCategory ◇— Product
Композиція*--частина не існує без цілогоOrder ◆— OrderItem
Атрибут ≈ поле таблиці / властивість моделі. Операція ≈ метод (calculateTotal(), isAvailable()).

09PlantUML і документ architecture.md

10Як усе складається в лаб. 2

    • Обрати тему (варіант 7 — інтернет-магазин) і заповнити паспорт системи.
    • Описати три UC у трьох формах; повний UC «Оформити замовлення» — з ≥10 кроками та ≥5 extensions.
    • Побудувати Use Case діаграму (PlantUML → PNG).
    • Побудувати Class діаграму (≥10 класів, усі типи відношень).
    • Зібрати docs/architecture.md, гілка feature/system-design, PR у main, зелений CI.
    • Звіт lab2/REPORT.md зі скріншотами з lab2/screenshots/.

Deliverables не змінюють PHP-код CI з лаб. 1 — лише каталог <code>docs/</code>, тому пайплайн має лишитися зеленим.

10Критерії якості діаграм

Перед здачею перевірте <strong>кількісні</strong> вимоги методички — їх легко рахувати на <code>.puml</code>:

ПеревіркаUse CaseClass
Актори на діаграміусі з паспорта—
UC на актора≥3 association—
Типи зв'язків UCassociation, include, extend, generalization—
Класи—≥10
Атрибути / операції—≥5 + ≥5 з типами
Відношення—наслідування, асоціація, агрегація, композиція

Читабельність PNG: шрифт не менше 12 pt, підписи не накладаються, кирилиця не «квадратиками». Якщо діаграма не вміщається на екран — групуйте UC у <code>rectangle</code>, скорочуйте довгі назви в <code>.puml</code>, але залишайте повні формулювання в <code>architecture.md</code>.

12Питання для самоконтролю

    • Чим Use Case відрізняється від окремого сценарію або user story?
    • Навіщо описувати межі системи, якщо «і так зрозуміло», що робить магазин?
    • У чому різниця include і extend? Наведіть приклад з інтернет-магазину.
    • Чому на діаграмі акторів Admin → Manager → Customer — це generalization, а не include?
    • Чим агрегація відрізняється від композиції для Category–Product і Order–OrderItem?
    • Навіщо на Class діаграмі вказувати типи атрибутів і параметрів операцій?
    • Як рядок stock_qty: Int на діаграмі пов'язаний із полем міграції Laravel?
    • Що має містити повна форма UC, чого немає в короткій?
    • Чому таблиці БД у множині (products), а класи в однині (Product)?
    • Як MVC допомагає не змішувати HTML, SQL і перевірку прав доступу?
    • Навіщо зберігати .puml разом із .png, якщо на GitHub показують лише картинку?
    • Як паспорт системи з лаб. 2 використовується в лаб. 3 (ключі масиву Product)?
    • Хто такий актор Платіжний шлюз і чому він не клас у доменній моделі магазину?
    • Скільки мінімум акторів і UC на актора вимагає методичка для Use Case діаграми?
    • Як таблиця відповідності Laravel у architecture.md зв'язує лаб. 2 і лаб. 5?
