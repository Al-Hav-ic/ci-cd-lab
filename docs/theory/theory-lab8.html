01Автентифікація vs авторизація

Це два різні питання, які часто плутають:

ПитанняМеханізмПриклад
Автентифікація — «Хто ви?»сесія / Bearer-токенвхід за email + password
Авторизація — «Чи маєте ви право?»Gates / Policies«чи можна Іванові видалити товар Олени?»

Автентифікація встановлює <strong>ідентичність</strong> користувача; авторизація визначає <strong>права</strong> цієї ідентичності над конкретним ресурсом. Користувач може бути автентифікованим (увійшов у систему), але неавторизованим для конкретної дії (не є власником запису).

Контекст лаб. 8: наш каталог допускає двох рівнів: перегляд — усім (гостям теж), а створення — будь-якому автентифікованому користувачу, оновлення та видалення — лише власнику запису. Це і є автентифікація (для «лише користувачам») + авторизація (для «лише власнику»).

02Сесійна автентифікація: стан на сервері

Класичний вебінтерфейс — <strong>stateful</strong>: сервер пам&#039;ятає, хто увійшов, у серверній сесії. Механізм:

    • Користувач надсилає email + password через HTML-форму (з CSRF-токеном з лаб. 7).
    • Auth::attempt($credentials) хешує пароль і порівнює з колонкою users.password.
    • При успіху Laravel зберігає ідентифікатор користувача в сесії та ставить у браузер session cookie.
    • Наступні запити браузер автоматично супроводжує цим cookie — middleware auth знаходить користувача через Auth::user().
Браузер: POST /login (email, password, _token)
   → Auth::attempt() → сесія створена → Set-Cookie: laravel_session=...
Браузер: GET /shop/create (Cookie: laravel_session=...)
   → middleware auth → Auth::user() → доступ дозволено

Паролі не зберігаються у відкритому вигляді: у моделі <code>User</code> cast <code>&#039;password&#039; =&gt; &#039;hashed&#039;</code> означає, що при записі Laravel автоматично застосує bcrypt; перевірка відбувається через <code>Hash::check()</code>.

03Токен-автентифікація та Laravel Sanctum

REST API — <strong>stateless</strong>: сервер не зберігає стан між запитами, бо клієнтом може бути мобільний застосунок, SPA або скрипт, які не використовують cookie. Для ідентифікації застосовують <strong>Bearer-токен</strong>.

Laravel Sanctum випускає персональні токени доступу:
    • Клієнт надсилає POST /login з email + password.
    • Сервер перевіряє облікові дані та викликає $user->createToken('api-token').
    • Sanctum генерує випадковий рядок, клієнту повертає його лише один раз (plainTextToken), а в таблицю personal_access_tokens зберігає SHA-256 хеш токена.
    • Кожен наступний запит клієнт супроводжує заголовком:
      • Authorization: Bearer <ваш_токен>
    • Middleware auth:sanctum на кожному запиті: витягує токен із заголовка, хешує його й шукає збіг у БД. Знайшов — пов'язує запит з відповідним користувачем; не знайшов — AuthenticationException (HTTP 401).
КритерійСесія (веб)Sanctum-токен (API)
Де зберігається ідентифікаторcookie браузерапередається клієнтом у заголовку
Стан серверасесія на серверібез стану (тільки запис у personal_access_tokens)
Канал передачіавтоматично, cookieвручну, Authorization: Bearer
Скасовуваннявидалення сесії$token->delete() — вихід для одного пристрою
Типовий споживачбраузер (SSR)мобільний застосунок, SPA, curl, Swagger UI

Токен — це «пароль для одного пристрою»: ним можна увійти з ноутбука й телефону одночасно, а «вихід» (<code>/logout</code>) відкликає лише поточний токен (<code>currentAccessToken()-&gt;delete()</code>).

04Session Fixation та гігієна сесій

Session Fixation — атака, коли зловмисник підсуває жертві відому йому сесію (наприклад, посилання з фіксованим ID сесії), щоб після входу жертви увійти в її акаунт. Захист — регенерація ідентифікатора сесії в момент підвищення привілеїв: 
Auth::attempt($credentials);
$request->session()->regenerate();   // новий ID сесії після входу

При виході з 系统 важливо знищити все:

Auth::logout();
$request->session()->invalidate();    // стерти дані сесії
$request->session()->regenerateToken(); // новий CSRF-токен
invalidate() завершує сесію (стара cookie стає недійсною), regenerateToken() замінює CSRF-токен, щоб старі форми, залишені у відкритих вкладках, не можна було використати після виходу.

05Авторизація: Gates та Policies

Laravel пропонує два декларативні механізми перевірки прав:

МеханізмЩо цеКоли застосовувати
Gateзамикання (closure), зареєстроване в AppServiceProvider, не прив'язане до моделіспільні дії: «доступ до панелі адміністратора»
Policyклас, що групує правила навколо однієї Eloquent-моделіCRUD конкретного ресурсу
Policy для Product має стандартний набір методів: 
viewAny(?User $user)  // чи бачити список
view(?User $user, Product $product) // чи бачити запис
create(User $user)    // чи створювати
update(User $user, Product $product) // чи редагувати
delete(User $user, Product $product) // чи видаляти

Сигнатура <code>?User $user</code> (nullable) означає: правило викликається навіть для <strong>гостей</strong> — так перегляд каталогу залишається публічним. Правила повертають <code>true</code>/<code>false</code>:

public function update(User $user, Product $product): bool
{
    return $user->id === $product->user_id; // лише власник
}

У контролері перевірка — один рядок:

$this->authorize('update', $product);

Це викликає <code>ProductPolicy::update()</code>; при <code>false</code> кидається <code>AuthorizationException</code> → HTTP <strong>403 Forbidden</strong>. Політику виявлено автоматично за конвенцією імен: <code>App\Models\Product</code> → <code>App\Policies\ProductPolicy</code>.

06Уніфікація авторизації у гібридній архітектурі

Головна перевага Laraveл-архітектури: <strong>один шар авторизації</strong> для вебу (сесії) та API (токени):

    • Web\ProductController (веб): $this->authorize('update', $product) → при забороні браузер отримує HTML-сторінку 403.
    • Api\ProductApiController (API): той самий виклик того самого ProductPolicy → API-клієнт отримує JSON 403.

Логіку змінюємо в одному місці — вона застосовується всюди. Це захищає від типового бага, коли правило оновили в API, а забули у вебі (або навпаки).

Різниця лише у <strong>вхідній автентифікації</strong>: веб-контролер діє від особи користувача з сесії (<code>auth()-&gt;id()</code>), API-контролер — від особи власника Bearer-токена (<code>$request-&gt;user()-&gt;id</code>). При створенні запису <strong>user_id призначає сервер</strong>, а не довіряє запиту:

$validated['user_id'] = auth()->id();        // веб
$validated['user_id'] = $request->user()->id; // API

07Декларативні директиви @auth, @guest, @can

Політика на сервері <strong>обов&#039;язкова</strong>, але не дає доброго UX: користувачу неприємно бачити кнопку «Видалити», яка при натисканні дає 403. У Blade є директиви, що читають ті самі правила:

@endguest

@endauth


@can(&#039;update&#039;, $product)

@endcan</code></pre>

08API Resources: контракт JSON-відповіді

Якщо повертати моделі Eloquent напряму (<code>return $product</code>), клієнт отримує всю внутрішню структуру таблиці: службові поля, зовнішні ключі, приховані дані. Це і незручно (контракт «плаває» при зміні схеми), і небезпечно.

API Resource (клас, успадкований від JsonResource) — шар трансформації між моделлю та JSON-відповіддю. Він визначає чіткий контракт: 
return [
    'id' => $this->id,
    'name' => $this->name,
    'price' => (float) $this->price,
    'owner_id' => $this->user_id,      // зовнішній ключ → семантичне поле
    'category' => $this->whenLoaded('category', fn () => [...]),
    'created_at' => $this->created_at?->toISOString(), // ISO 8601
];

Що дає ресурс: клієнтський код не ламається при рефакторингу БД; зовнішні ключі перейменовуються у зрозумілі поля (<code>user_id</code> → <code>owner_id</code>); типи нормалізуються (decimal → float, дати → ISO 8601); зайвого немає (паролі, службові колонки не потрапляють у відповідь навіть випадково).

09Проблема N + 1 запитів та whenLoaded

N + 1 — типова вада ORM: для списку з 10 товарів виконується 1 запит списку + 10 окремих запитів категорій (по одному на товар). Розв'язання — жадібне завантаження (Eager Loading) одним додатковим запитом: 
Product::with(['category:id,name', 'reviews:id,product_id,rating,text'])
    ->paginate(10);

У ресурсі <code>whenLoaded(&#039;category&#039;, ...)</code> додає зв&#039;язок у JSON <strong>лише якщо</strong> контролер його завантажив:

    • контролер забув with('category') → поле category взагалі відсутнє у відповіді (немає прихованого N + 1);
    • контролер завантажив → клієнт отримує вкладений об'єкт.

Так ресурс «примушує» контролер свідомо планувати запити, а клієнт бачить передбачуваний контракт.

10Специфікація OpenAPI та Swagger UI

OpenAPI Specification (OAS) — галузевий стандарт опису REST API: маршрути, методи, параметри, тіла запитів, коди відповідей і схеми безпеки у JSON/YAML. Документація, написана вручну, швидко застаріває; специфікація, згенерована з коду, завжди збігається з реальністю.

Пакет <strong>l5-swagger</strong> генерує специфікацію з PHP 8 Attributes (<code>#[OA\Get(...)]</code>, <code>#[OA\Post(...)]</code>) прямо над методами контролерів і віддає її через інтерактивну сторінку <strong>Swagger UI</strong> на <code>/api/documentation</code>:

    • Базові атрибути (OA\Info, OA\Server, OA\SecurityScheme) — у базовому класі контролерів: заголовок документації, адреса сервера /api/v1 і схема безпеки bearerAuth (дає кнопку Authorize).
    • Атрибути над методами (OA\Get, OA\Post, OA\Put, OA\Delete) описують ендпоінт: теги, параметри, приклади тіл запитів, можливі відповіді (201/401/403/422).
    • security: [["bearerAuth" => []]] позначає ендпоінт як захищений.
Swagger UI — не просто сторінка з текстом: це інтерактивний консоль. Кнопка Authorize приймає реальний Bearer-токен (отриманий через POST /login), після чого кнопка Execute кожної операції виконує справжні HTTP-запити до сервера й показує фактичні коди відповідей (201 Created, 403 Forbidden) і тіла JSON. Тестувальник може перевірити контракт без написання жодного рядка коду.

11HTTP 401 vs 403

Обидва статуси — «відмова», але з різним змістом:

СтатусЗначенняКоли виникає у нас
401 Unauthorized«Хто ви? Не впізнано» — відсутній/невірний токенPOST /api/v1/products без заголовка Authorization
403 Forbidden«Ви впізнані, але права немає» — токен валідний, дія забороненаDELETE чужого товару з валідним токеном

Мнемоніка: 401 — проблема <strong>автентифікації</strong>; 403 — проблема <strong>авторизації</strong>. Правильний API повертає 401 для неавтентифікованих запитів і 403 для автентифікованих, але без прав: клієнт за кодом розуміє, що робити (повторно увійти або не намагатись).

12Версіонування API

Маршрути API живуть у <code>routes/api.php</code>, якому Laravel автоматично додає префікс <code>/api</code>. Ендпоінти згруповано під <code>/api/v1</code>:

Route::prefix('v1')->group(function (): void {
    Route::post('/login', [AuthController::class, 'login']);
    Route::get('/products', [ProductApiController::class, 'index']);
    Route::middleware('auth:sanctum')->group(function (): void {
        Route::post('/products', [ProductApiController::class, 'store']);
    });
});

Навіщо версіювати: коли в майбутньому зміниться контракт (наприклад, поле <code>price</code> стане об&#039;єктом з валютою), старі клієнти не зламаються — вони продовжать бити <code>/api/v1</code>, а нові перейдуть на <code>/api/v2</code>. Це звичайна гігієна публічних API.

Публічні маршрути (реєстрація, вхід, читання товарів і довідників) та захищені (<code>auth:sanctum</code> — вихід, створення/редагування/видалення) розділено прямо в групі.

13Feature-тести захисту

Безпеку перевіряють автоматично, а не очима. <code>ProductApiSecurityTest</code> покриває ключові сценарії:

// 401: без токена створення заборонено
$this->postJson('/api/v1/products', [...])->assertStatus(401);

// 403: інший користувач не може видалити чужий запис
Sanctum::actingAs($intruder);
$this-&gt;deleteJson(&quot;/api/v1/products/{$product-&gt;id}&quot;)-&gt;assertStatus(403);


// веб: гостьа перенаправляють на форму входу
$this-&gt;get(&#039;/shop/create&#039;)-&gt;assertRedirect(&#039;/login&#039;);


// веб: 403 на пряме звернення до чужого edit
$this-&gt;actingAs($intruder)-&gt;get(&quot;/shop/{$product-&gt;id}/edit&quot;)-&gt;assertStatus(403);</code></pre>


Методи <code>postJson()</code>/<code>deleteJson()</code> налаштовують заголовок <code>Accept: application/json</code>, щоб сервер повертав JSON-помилки, а не HTML-сторінку — саме так працює реальний API-клієнт. <code>Sanctum::actingAs()</code> імітує запит з токеном без реального випуску.

15Як усе складається в лаб. 8

Схема гібридного захисту, який реалізовано в репозиторії:

                    ┌──────────────────────────┐
   Браузер (SSR) ──▶│ cookie сесії   │▶ Web\ProductController ─┐
   curl/Swagger ───▶│ Authorization: Bearer │▶ Api\ProductApiController ─┤
                    └──────────────────────────┘                │
                                                  auth (web) / auth:sanctum (api)
                                                                ▼
                                              ProductPolicy::update/delete
                                                     user_id === owner
                                                    /            \
                                                 false          true
                                                  ▼               ▼
                                     403 HTML / 403 JSON   операція виконується
    • Автентифікація розведена: сесії для Blade-інтерфейсу (/login, /register), Bearer-токени Sanctum для API (/api/v1/login, /api/v1/register).
    • Авторизація — єдина: ProductPolicy, викликана $this->authorize() з обох контролерів.
    • Дані віддаються клієнту через ProductResource з жадібно завантаженими зв'язками.
    • Документація згенерована з тих самих контролерів у /api/documentation й перевірена вручну у Swagger UI.
    • Безпека підтверджена автоматично: ProductApiSecurityTest (401/403) та оновлений CatalogViewTest (redirect, 403 веб).

    • У чому принципова відмінність між сесійною автентифікацією та токен-автентифікацією через Sanctum для REST API?
    • Як механізм перевірки токена Sanctum працює на рівні БД та HTTP-заголовків?
    • Чим Gate відрізняється від Policy і коли доцільний кожен із них?
    • Яку роль відіграє шар JsonResource між моделями Eloquent та клієнтом API?

    • Для чого потрібна специфікація OpenAPI і які переваги дає Swagger UI?

18Відповіді

    • Сесія зберігає стан на сервері та ідентифікує користувача через cookie автоматично; токен — без стану: клієнт сам передає Authorization: Bearer <token> у кожному запиті, сервер лише перевіряє хеш у БД. Сесія — для браузера (SSR), токен — для API-клієнтів (SPA, мобільні, curl).
    • createToken() зберігає SHA-256 хеш токена у personal_access_tokens (з прив'язкою до user_id); на кожному запиті middleware auth:sanctum хешує токен із заголовка Authorization: Bearer і шукає збіг у таблиці — знайдений запис визначає користувача.
    • Gate — замикання для дій, не прив'язаних до моделі (доступ до адмін-панелі); Policy — клас правил навколо конкретної моделі (update/delete власника). Policy — для CRUD ресурсу, Gate — для загальних перевірок.
    • JsonResource — шар трансформації: задає чіткий контракт JSON (які поля, у якому форматі), приховує внутрішню структуру БД, перейменовує ключі (user_id → owner_id), умовно включає зв'язки через whenLoaded().
    • Поєднати Eager Loading у контролері (with('category')) та whenLoaded('category') у ресурсі: поле потрапляє у відповідь лише коли зв'язок завантажено одним додатковим запитом; без нього поле відсутнє, і прихованого N + 1 не виникає.
    • OpenAPI — стандартизований машинозчитуваний опис ендпоінтів; він не застаріває, бо генерується з атрибутів контролерів. Swagger UI візуалізує специфікацію, дозволяє авторизуватися Bearer-токеном і виконувати реальні запити (201/403) без написання коду.
    • 401 — «не впізнано» (немає токена, невірні облікові дані): клієнту треба пройти автентифікацію. 403 — «впізнано, але заборонено» (політика відмовила): повторна автентифікація не допоможе.
    • postJson()/deleteJson() ставлять Accept: application/json, тому валідаційні помилки та винятки повертаються як JSON (422/401/403), як для реального API-клієнта, а не редірект на HTML-сторінку.
    • regenerate() після входу міняє ID сесії — захист від Session Fixation. invalidate() при виході стирає дані сесії, regenerateToken() міняє CSRF-токен, щоб старі форми у відкритих вкладках стали недійсними.
