01Навіщо ORM: Eloquent у Laravel

ORM (Object-Relational Mapping) — шар, який зіставляє таблиці БД з об'єктами мови програмування. Замість ручного SELECT * FROM products WHERE id = ? і складання масиву розробник пише Product::find($id) й отримує об'єкт із методами та зв'язками. Eloquent — вбудована ORM Laravel. Її робота будується на трьох ідеях:
    • Модель = таблиця. Клас Product за замовчуванням відповідає таблиці products (snake_case, множина).
    • Об'єкт = рядок. Екземпляр моделі містить атрибути одного рядка; $product->price читає колонку price.
    • Зв'язок = метод. $product->category повертає об'єкт Category, а не просто число category_id.

Порівняння підходів:

ПідхідПрикладПлюсиМінуси
Сирий SQL$pdo->query('SELECT ...')повний контрольручне екранування, багато коду
Query BuilderDB::table('products')->where(...)безпечні параметринемає об'єктів і зв'язків
EloquentProduct::with('category')->find($id)об'єкти, зв'язки, події, casts«магія», потрібно стежити за N+1

У лаб. 5 контролери повертали масиви з пам&#039;яті: після завершення запиту дані зникали. У лаб. 6 Eloquent зберігає їх у БД, тому <code>GET</code> після <code>POST</code> бачить створений товар.

Важливо: ORM не скасовує знання SQL. Складні звіти, EXPLAIN, індекси й транзакції все одно проєктуються на рівні БД.

02Підключення бази даних

Конфігурація — у <code>config/database.php</code>, значення — у <code>.env</code>:

DB_CONNECTION=sqlite
# Для MySQL:
# DB_CONNECTION=mysql
# DB_HOST=127.0.0.1
# DB_PORT=3306
# DB_DATABASE=ci_cd_lab
# DB_USERNAME=root
# DB_PASSWORD=

Laravel підтримує SQLite, MySQL/MariaDB, PostgreSQL, SQL Server. У лабораторній використано <strong>SQLite</strong>:

    • нульове налаштування — достатньо файлу database/database.sqlite;
    • той самий драйвер у GitHub Actions, тому локальний і CI-прогін ідентичні;
    • обмеження: частина ALTER TABLE операцій відрізняється від MySQL, тому міграції пишуться обережно.

Перевірка підключення:

php artisan db:show
php artisan migrate:status

Якщо файлу немає, його створюють заздалегідь:

php -r "file_exists('database/database.sqlite') || touch('database/database.sqlite');"

03Міграції

Міграція — PHP-клас, який описує зміну схеми: створення таблиці, додавання колонки, індексу тощо. Міграції виконуються по черзі й фіксуються в службовій таблиці migrations, тому Laravel знає, що вже застосовано.

3.1. Створення та запуск

php artisan make:migration create_products_table
php artisan migrate
php artisan migrate:status
php artisan migrate:rollback
php artisan migrate:fresh --seed
    • migrate — застосувати нові міграції;
    • migrate:status — показати, які виконані (Ran), а які ні (Pending);
    • migrate:rollback — відкотити останній батч;
    • migrate:fresh — видалити всі таблиці й виконати міграції з нуля;
    • --seed — після міграцій запустити DatabaseSeeder;
    • migrate --force — запуск у production/CI без інтерактивного підтвердження.

      • 3.2. Структура міграції

      public function up(): void
{
    Schema::create('products', function (Blueprint $table) {
        $table->id();
        $table->foreignId('category_id')->constrained()->cascadeOnDelete();
        $table->string('sku')->unique();
        $table->string('name');
        $table->decimal('price', 10, 2);
        $table->unsignedInteger('stock_qty')->default(0);
        $table->boolean('is_active')->default(true);
        $table->timestamps();

      $table-&gt;index([&#039;is_active&#039;, &#039;price&#039;]);
    });
}
      

      public function down(): void
{
    Schema::dropIfExists(&#039;products&#039;);
}</code></pre>
      
up() описує пряму зміну, down() — зворотну. Добре написана міграція дозволяє відкотитися без втрати інших таблиць.

      3.3. Типи колонок і ключі
      

      МетодПризначення
      $table->id()BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
      $table->foreignId('x')->constrained()FK на x_id → таблицю, визначену за іменем
      $table->string('name', 255)VARCHAR
      $table->text('description')->nullable()текст, дозволяє NULL
      $table->decimal('price', 10, 2)гроші з двома знаками після коми
      $table->boolean('is_active')->default(true)прапорець
      $table->timestamps()created_at, updated_at
      $table->unique([...])складений унікальний індекс
      $table->index([...])звичайний індекс
      

      3.4. Порядок і залежності
      

      Таблиця з зовнішнім ключем має створюватися <strong>після</strong> батьківської. Саме тому в лаб. 6 спочатку йдуть <code>categories</code>, <code>users</code>, потім <code>products</code>, <code>customers</code>, а вже потім <code>orders</code>, <code>order_items</code>, <code>payments</code>, <code>discount_order</code>. Інакше SQLite/MySQL не зможе створити FK.
      

      Для зв&#039;язку 1:1 унікальність забезпечує <code>-&gt;unique()</code> на зовнішньому ключі:
      

      $table->foreignId('user_id')->unique()->constrained()->cascadeOnDelete();
      

      3.5. Каскади
      

    • cascadeOnDelete() — видалення батька видаляє дітей (замовлення → позиції, замовлення → платіж, pivot-рядки).
      • 

    • nullOnDelete() — видалення батька обнуляє FK (категорія → підкатегорія, якщо не хочемо втрачати дерево).
      • 

    • restrictOnDelete() — забороняє видалення, поки є залежні рядки.
      •

Вибір каскаду — бізнес-рішення, а не технічне: не можна допустити «сирітських» позицій замовлення.

04Моделі Eloquent

4.1. Угоди та налаштування

class Product extends Model
{
    use HasFactory;

protected $fillable = [
        &#039;category_id&#039;, &#039;sku&#039;, &#039;name&#039;, &#039;description&#039;,
        &#039;price&#039;, &#039;stock_qty&#039;, &#039;is_active&#039;,
    ];


protected $casts = [
        &#039;price&#039; =&gt; &#039;float&#039;,
        &#039;stock_qty&#039; =&gt; &#039;integer&#039;,
        &#039;is_active&#039; =&gt; &#039;boolean&#039;,
    ];
}</code></pre>


    

      

    • $fillable — «білий список» полів для create() / fill(). Захищає від масового запису службових полів (id, role).
      • 

    • $guarded — протилежність; у навчальному коді краще явний $fillable.
      • 

    • $casts — перетворення типів під час читання/запису: decimal приходить як рядок, тому float; 0/1 → bool; дата → Carbon.
      • 

    • $table — задається лише якщо ім'я таблиці не збігається з угодою (products).
      • 

    • $primaryKey, $incrementing, $keyType — для нестандартних ключів.
      • 

    • $timestamps = false — вимкнути created_at/updated_at.
      • 

    • $hidden — приховати поля з JSON (наприклад, password).
      • 

    



4.2. Route model binding


public function show(Product $product): JsonResponse
{
    $product->load('category');
    return response()->json(['status' => 'success', 'data' => $product]);
}


Laravel сам викликає <code>Product::findOrFail($id)</code> за значенням <code>{product}</code> з маршруту. Якщо запису немає — генерується <code>ModelNotFoundException</code>, який перетворюється на <strong>404</strong>. Це прибирає ручні перевірки <code>if (! $product)</code>.

$cat->id;        // null — рядка ще немає
$cat->save();    // INSERT
$cat->id;        // 6 — Eloquent присвоїв ключ

$cat2 = Category::create([...]); // new + save в один виклик</code></pre>

create() використовує $fillable; якщо поле не вказане у списку, воно буде проігнороване.

Побудова запиту — «ланцюжок»:

$products = Product::query()
    ->with(['category:id,name,slug', 'reviews:id,product_id,rating'])
    ->when($request->filled('category_id'),
        fn ($q) => $q->where('category_id', $request->integer('category_id')))
    ->when($request->filled('search'),
        fn ($q) => $q->where('name', 'like', '%'.$request->string('search').'%'))
    ->when($request->boolean('active_only', true),
        fn ($q) => $q->where('is_active', true))
    ->orderBy('name')
    ->paginate(15);
when() виконує замикання лише тоді, коли умова істинна, — це акуратніше за if навколо кожного where.

06Зв'язки 1:1, 1:M, M:M

6.1. Один-до-одного (1:1)

Приклад: користувач має один профіль покупця.

// User
public function customer(): HasOne
{
    return $this->hasOne(Customer::class);
}

// Customer
public function user(): BelongsTo
{
    return $this-&gt;belongsTo(User::class);
}</code></pre>


У БД це <code>customers.user_id</code> з <code>UNIQUE</code>. Без унікальності це вже був би 1:M (багато профілів на одного користувача).


Другий приклад — <code>Order</code> ↔ <code>Payment</code>: <code>payments.order_id</code> унікальний, <code>Order::payment(): HasOne</code>, <code>Payment::order(): BelongsTo</code>.


6.2. Один-до-багатьох (1:M)


// Category
public function products(): HasMany
{
    return $this->hasMany(Product::class);
}

// Product
public function category(): BelongsTo
{
    return $this-&gt;belongsTo(Category::class);
}</code></pre>

HasMany — на боці «один», BelongsTo — на боці «багато» (там, де зберігається FK). Метод belongsTo завжди живе в моделі, яка містить *_id.

Створення дочірнього запису через зв&#039;язок автоматично підставляє FK:


$product = $category->products()->create([
    'name' => 'Бездротова клавіатура',
    'sku' => 'KB-PERIPH-01',
    'price' => 1450.00,
    'stock_qty' => 15,
]);
// $product->category_id === $category->id


6.3. Багато-до-багатьох (M:M)


Потрібна проміжна (pivot) таблиця. У лаб. 6 — <code>discount_order</code>:


// Order
public function discounts(): BelongsToMany
{
    return $this->belongsToMany(Discount::class)->withTimestamps();
}

// Discount
public function orders(): BelongsToMany
{
    return $this-&gt;belongsToMany(Order::class)-&gt;withTimestamps();
}</code></pre>


Ім&#039;я таблиці Laravel будує з імен моделей в алфавітному порядку: <code>discount</code> + <code>order</code> → <code>discount_order</code>. Якщо таблиця називається інакше, її передають другим аргументом: <code>belongsToMany(Discount::class, &#039;order_discount&#039;)</code>.


Основні операції:


МетодДія
attach($id)додати зв'язок (дублікат викличе помилку UNIQUE)
detach($id)видалити один зв'язок
sync([$ids])зробити набір зв'язків рівним переданому (додає й видаляє)
syncWithoutDetaching([$ids])додати лише відсутні
toggle([$ids])перемкнути наявність
pivotдоступ до полів проміжної таблиці

sync() — ключовий метод для редагування: він не чіпає наявні зв'язки, які є в новому списку, видаляє зайві й додає нові. Саме тому PUT /orders/{id}/discounts викликає $order->discounts()->sync($ids).

$order->discounts()->attach([1, 2]);
$order->discounts()->sync([1]);       // знижка 2 зникла
$order->discounts()->pluck('code');   // ['SAVE-2216']


6.4. Самопосилання


Категорії утворюють дерево:


public function parent(): BelongsTo
{
    return $this->belongsTo(self::class, 'parent_id');
}

public function children(): HasMany
{
    return $this-&gt;hasMany(self::class, &#039;parent_id&#039;);
}</code></pre>


Без явного <code>parent_id</code> Laravel шукав би <code>category_id</code>, тому другий аргумент обов&#039;язковий.

07Жадібне завантаження і проблема N+1

N+1 — ситуація, коли для списку з N записів виконується 1 запит на список і ще N запитів на зв'язки. Для 100 товарів без with('category') буде 101 запит. 
// Погано: 1 + N запитів
$products = Product::all();
foreach ($products as $product) {
    echo $product->category->name; // щоразу новий SELECT
}

// Добре: 2 запити
$products = Product::with(&#039;category&#039;)-&gt;get();</code></pre>


Види завантаження:


МетодКоли працює
with('relation')одразу, при побудові запиту
load('relation')після отримання моделі
loadMissing('relation')лише якщо зв'язок ще не завантажений
$product->categoryліниве (lazy) завантаження «на вимогу»
withCount('reviews')додає reviews_count без завантаження всіх відгуків


У лаб. 6 <code>ProductController@index</code> завантажує <code>category</code> і <code>reviews</code>, <code>OrderController@show</code> — <code>customer.user</code>, <code>items.product</code>, <code>payment</code>, <code>discounts</code>. Це фіксована кількість запитів незалежно від кількості рядків.


Перевірити кількість запитів можна через <code>DB::listen()</code> або Laravel Debugbar. У тестах достатньо переконатися, що відповідь містить вкладені об&#039;єкти.

09Цілісність даних і транзакції

9.1. Рівні захисту

РівеньІнструментЩо гарантує
СхемаNOT NULL, UNIQUE, FOREIGN KEY, CHECKкоректність на рівні БД
Модель$fillable, $casts, валідаціякоректність на рівні застосунку
Бізнес-логікатранзакції, DB::transaction()атомарність кількох операцій

Валідація в контролері не замінює обмежень БД: паралельні запити можуть пройти валідацію одночасно, тому <code>UNIQUE</code> — остання лінія захисту.

9.2. Транзакції

Створення замовлення — це кілька <code>INSERT</code> (замовлення, позиції, pivot, перерахунок). Якщо один крок упаде, БД не повинна залишитися в напівстані:

$order = DB::transaction(function () use ($validated): Order {
    $order = Order::create([...]);

foreach ($validated[&#039;items&#039;] as $row) {
        OrderItem::create([...]);
    }


$order-&gt;discounts()-&gt;sync($validated[&#039;discount_ids&#039;] ?? []);
    $this-&gt;recalculateTotals($order);


return $order;
});</code></pre>

DB::transaction() виконує BEGIN, COMMIT у разі успіху та ROLLBACK у разі винятку. Це стандартний спосіб зберегти узгодженість.

9.3. Перерахунок підсумку


$subtotal = $order->items->sum(
    fn (OrderItem $item) => $item->quantity * $item->unit_price,
);
$percent = min(100.0, (float) $order->discounts->sum('percent'));
$discountAmount = round($subtotal * $percent / 100, 2);

$order-&gt;update([
    &#039;total_amount&#039; =&gt; round($subtotal - $discountAmount, 2),
    &#039;discount_amount&#039; =&gt; $discountAmount,
]);</code></pre>


Сума відсотків обмежена 100 %, інакше знижки могли б зробити замовлення від&#039;ємним. Округлення до копійок виконується на кожному етапі, щоб уникнути похибки <code>float</code>.

CI перевіряє не лише код, а й те, що міграції виконуються на чистій БД. Якщо хтось забув міграцію для нової колонки, тести впадуть ще до merge.


10.4. Чому тести мають бути детермінованими


Фабрика може генерувати випадкові значення (<code>is_active =&gt; fake()-&gt;boolean(90)</code>). Якщо тест очікує 3 товари в каталозі, а каталог фільтрує неактивні, результат залежить від випадковості. Правильне рішення — явно зафіксувати потрібний стан:


Product::factory()->count(3)->create(['is_active' => true]);


Тест має перевіряти логіку, а не удачу.

15Відповіді

    • ORM зіставляє рядки таблиць з об'єктами, дає зв'язки, casts, події та route binding. Query Builder працює з таблицями й масивами, але не знає про моделі та зв'язки; Eloquent будується поверх нього.
    • SQLite не потребує сервера й працює у файлі, тому однаково поводиться локально та в GitHub Actions. Обмеження: слабші ALTER TABLE, менше типів, інша поведінка конкурентного запису.
    • up() застосовує зміну (створює таблицю, додає колонку), down() повертає схему до попереднього стану. Це дозволяє rollback.
    • Бо products.category_id — зовнішній ключ на categories.id; СУБД не створить FK на неіснуючу таблицю.
    • Зовнішній ключ у дочірній таблиці оголошено UNIQUE: для одного батька фізично можливий лише один рядок.
    • $fillable захищає від масового запису зайвих полів (наприклад, role), $casts приводить значення до потрібного типу (float, bool, Carbon).
    • Laravel бере імена моделей в алфавітному порядку й з'єднує через _: discount + order → discount_order.
    • attach() додає зв'язок, detach() видаляє, sync() робить набір рівним переданому: додає нові, видаляє зайві, залишає спільні.
    • N+1 — один запит на список плюс окремий запит на кожен зв'язок. with('relation') завантажує всі зв'язки одним-двома запитами.
    • Замовлення створюється кількома INSERT; транзакція гарантує, що при помилці не залишиться часткових даних (замовлення без позицій або без платежу).
    • RefreshDatabase будує чисту схему й відкочує зміни після тесту. Каталог фільтрує is_active, тому фабрика з випадковим значенням давала б різну кількість — стан треба фіксувати явно.
    • CI створює SQLite-файл і виконує php artisan migrate --force перед тестами; будь-яка неузгодженість міграцій валить build.
