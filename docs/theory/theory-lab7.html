01SSR та MVC: де живе View

Патерн MVC (Model–View–Controller) розподіляє вебдодаток на три шари:
    • Model — дані та правила роботи з ними (у нас — моделі Eloquent з лаб. 6: Product, Category, Order...).
    • View — представлення, тобто те, що бачить користувач: HTML-сторінки, таблиці, форми.
    • Controller — проміжний шар: приймає запит, звертається до моделей, обирає подання й передає туди дані.

Існує два принципово різні способи отримати UI в браузері:

КритерійSSR (Laravel + Blade)SPA (React/Vue + JSON API)
Де рендериться HTMLна серверіу браузері, через JavaScript
Мова шаблонівBlade (.blade.php)JSX/шаблони компонентів
Передані даніготовий HTMLJSON, збірка DOM на клієнті
Навігаціяповне завантаження сторінкимаршрутизація без перезавантаження
SEO та «перша фарба»одразу готовий контентпотрібне додаткове SSR/прейрендер
Стан додаткуу сесії на серверіна клієнті (store, hooks)
SSR (Server-Side Rendering) означає: кожен запит обробляється сервером, який збирає повну HTML-сторінку й віддає її браузеру. Blade-шаблонізатор Laravel — інструмент саме для SSR. Це не «застарілий» підхід: для адмінок, каталогів, звітів SSR простіший, безпечніший і швидше віддає першу сторінку.
Контекст лаб. 7: у лаб. 5 API-контролери повертали JsonResponse — споживачем був програмний клієнт. Тепер ті самі сутності обслуговують людину: контролери повертають view(...), а дані форм подорожують через сесію. API лишається недоторканим — обидва режими працюють паралельно.

02Життєцикл SSR-запиту

Запит на сторінку каталогу /shop проходить такий шлях:
    • public/index.php — front controller; створюється застосунок Laravel.
    • Middleware — напр., перевірка сесії (для CSRF), запуск сесії для old() і flash.
    • Router — routes/web.php: GET /shop → Web\ProductController@index.
    • Controller — виконує запит до БД (Product::with('category')->paginate(10)) і викликає view('shop.index', [...]).
    • Blade-компіляція — шаблон перетворюється на звичайний PHP-код (кешується в storage/framework/views).
    • Рендер — PHP-код виконується, дані «втілюються» в HTML.
    • Response — готовий HTML відправляється браузеру.
Браузер → HTTP-запит → Router → Controller (+Model) → View (Blade)
                                                        ↓
Браузер ← HTTP-відповідь (HTML) ← Response ← компільований PHP

Жодного JavaScript на сервері не виконується, а браузер отримує вікно, яке вже повністю намальоване.

03Шаблонізатор Blade: синтаксис і компіляція

Blade — вбудований шаблонізатор Laravel. Файли з розширенням .blade.php зберігаються в resources/views. На відміну від Twig, Blade не забороняє чистий PHP, але пропонує декларативні директиви (починаються з @) для типових завдань. При першому виклику шаблон компілюється у PHP і кешується — далі виконується тільки компільована версія.

Ключові конструкції:

КонструкціяЩо робить
{{ $var }}вивід з автоматичним htmlspecialchars() — захист від XSS
{!! $html !!}вивід сирого HTML (тільки для довіреного контенту)
@if / @elseif / @else / @endifумови
@foreach ... @endforeachцикл; всередині доступний об'єкт $loop ($loop->first, $loop->iteration)
@forelse ... @empty ... @endforelseцикл з запасним варіантом для порожньої колекції
@empty($var) / @isset($var)перевірка порожньості/наявності
@csrf, @method('PUT')приховані поля форм (нижче)
@error('field') ... @enderrorблок, що спрацьовує за наявності помилки валідації
Приклад з нашого каталогу resources/views/shop/index.blade.php: 
@forelse ($products as $product)
    <tr>
        <td>{{ $product->id }}</td>
        <td>{{ $product->name }}</td>
        <td>{{ $product->category->name ?? 'Немає' }}</td>
        <td>{{ number_format($product->price, 2) }}</td>
        <td>
            @if ($product->is_active)
                <span class="badge bg-success">активний</span>
            @else
                <span class="badge bg-secondary">приховано</span>
            @endif
        </td>
    </tr>
@empty
    <tr><td colspan="7" class="text-center">Записів не знайдено.</td></tr>
@endforelse
Безпека за замовчуванням: конструкція {{ }} екранує вивід. Якщо у формі коментар покупець напише <script>alert(1)</script>, Blade покаже цей текст як текст, а не виконає скрипт. {!! !!} застосовується лише там, де HTML перевірений розробником.

04Успадкування макетів (layouts)

Вебдодаток має спільні елементи: шапку з навігацією, підвал, підключення CSS. Дублювати їх у кожній сторінці — погана практика. Blade вирішує це механізмом успадкування:

    • Базовий макет resources/views/layouts/app.blade.php містить каркас HTML і «мітки вставки» — @yield('content') та @yield('title', 'за замовчуванням').
    • Дочірні шаблони оголошують @extends('layouts.app') і наповнюють секції через @section('content') ... @endsection.
Наш макет layouts/app.blade.php (скорочено): 
<nav class="navbar navbar-expand-lg navbar-dark bg-dark mb-4">
    <div class="container">
        <a class="navbar-brand" href="{{ route('home') }}">Супермаркет</a>
        <ul class="navbar-nav me-auto">
            <li><a class="nav-link" href="{{ route('shop.index') }}">Каталог</a></li>
            <li><a class="nav-link" href="{{ route('manage.categories.index') }}">Категорії</a></li>
            <!-- ... покупці, знижки, замовлення, відгуки -->
        </ul>
    </div>
</nav>
<div class="container">
    @if (session('success'))
        <div class="alert alert-success alert-dismissible fade show">
            {{ session('success') }}
            <button type="button" class="btn-close" data-bs-dismiss="alert"></button>
        </div>
    @endif
    @yield('content')
</div>

Дочірнє подання:

@extends('layouts.app')

@section(&#039;title&#039;, &#039;Каталог товарів&#039;)


@section(&#039;content&#039;)
    &lt;h1&gt;Каталог товарів&lt;/h1&gt;
    ...
@endsection</code></pre>

Flash-повідомлення живуть саме в макеті: контролер після успішної дії робить redirect()->route(...)->with('success', 'Товар створено!'), значення пишеться в сесію, макет читає session('success') і показує зелене alert-success лише один раз (на наступному запиті воно зникає).

05Blade-компоненти

Компонент — сучасна альтернатива @include: самодостатній блок HTML з власними атрибутами-пропсами. Анонімні компоненти лежать у resources/views/components і викликаються тегами з префіксом x-. Наш компонент поля вводу components/form/input.blade.php: 
@props(['name', 'label', 'type' => 'text', 'value' => ''])

&lt;div class=&quot;mb-3&quot;&gt;
    &lt;label for=&quot;{{ $name }}&quot; class=&quot;form-label&quot;&gt;{{ $label }}&lt;/label&gt;
    &lt;input
        type=&quot;{{ $type }}&quot;
        name=&quot;{{ $name }}&quot;
        id=&quot;{{ $name }}&quot;
        class=&quot;form-control @error($name) is-invalid @enderror&quot;
        value=&quot;{{ old($name, $value) }}&quot;
        {{ $attributes }}
    &gt;
    @error($name)
        &lt;div class=&quot;invalid-feedback&quot;&gt;{{ $message }}&lt;/div&gt;
    @enderror
&lt;/div&gt;</code></pre>


Використання у формі:


<x-form.input name="name" label="Назва товару" required/>
<x-form.input name="price" label="Ціна, грн" type="number" step="0.01" :value="$product->price"/>


Розбір:


    

      

    • @props оголошує пропси та значення за замовчуванням; :value="..." — «динамічний» пропс (вираз PHP, а не рядок).
      • 

    • {{ $attributes }} — додаткові атрибути (required, step, min...).
      • 

    • $slot — вміст між <x-...>...</x-...>, доступний всередині компонента; у компонентах «обгортках» (картка, модальне вікно) на його місце стає вкладений HTML.
      • 

    


Компонент прибрав дублювання: правила «підставити old(), підсвітити помилку, показати текст помилки» описані один раз, а не в кожній формі.

06HTML-форми та Method Spoofing

Стандартна HTML-форма вміє лише GET і POST. Але RESTful-маршрутизація вимагає PUT/PATCH для оновлення та DELETE для видалення. Laravel вирішує це механізмом Method Spoofing: директива @method('PUT') додає приховане поле _method, яке маршрутизатор розпізнає й трактує запит як PUT/DELETE. 
<!-- Редагування: POST-форма, що подає себе як PUT -->
<form action="{{ route('shop.update', $product->id) }}" method="POST">
    @csrf
    @method('PUT')
    ...
</form>

&lt;!-- Видалення прямо зі списку --&gt;
&lt;form action=&quot;{{ route(&#039;shop.destroy&#039;, $product-&gt;id) }}&quot; method=&quot;POST&quot;
      onsubmit=&quot;return confirm(&#039;Дійсно видалити?&#039;);&quot;&gt;
    @csrf
    @method(&#039;DELETE&#039;)
    &lt;button type=&quot;submit&quot; class=&quot;btn btn-sm btn-danger&quot;&gt;Видалити&lt;/button&gt;
&lt;/form&gt;</code></pre>

Результат: Route::resource('shop', ...) працює коректно — update отримує запит PUT, destroy — DELETE, хоча фізично браузер відправляв POST.

Вибір зв&#039;язків у формах:


Зв'язокHTML-елементДані на сервері
1:M (Product → Category, Order → Customer)<select> зі списком батьківських записіводне поле category_id / customer_id
M:M (Order ↔ Discount)група <input type="checkbox" name="discount_ids[]">масив id; sync() оновлює pivot discount_order

07CSRF-захист форм

CSRF (Cross-Site Request Forgery) — атака, за якої зловмисна сторінка змушує браузер залогіненого користувача відправити запит на наш сайт (напр., POST-запит на видалення товару). Браузер автоматично докладає cookies сесії, тож сервер «вірячить», що це сам користувач. Захист — токен CSRF: унікальне випадкове значення, збережене в сесії, яке має бути присутнім у запиті. Директива @csrf додає приховане поле: 
<input type="hidden" name="_token" value="xK2f...9dQ">
Middleware ValidateCsrfToken порівнює на кожному POST/PUT/PATCH/DELETE значення поля з сесією. Якщо не збігається — запит відхиляється з помилкою 419 (Page Expired), до контролера він не доходить.

Слідства для практики: у curl-сценаріях чи тестах доводиться окремо витягувати токен із форми; у feature-тестах Laravel перевіряє CSRF автоматично або в тестовому середовищі його пропускає.

08Валідація та життєвий цикл помилок

Класичний цикл роботи з формою:

GET /shop/create  →  форма порожня
POST /shop        →  validate() → якщо помилки:
                        редірект назад + помилки та old() у сесії
                  →  GET /shop/create знову:
                        @error показує повідомлення, old() повертає введене
                  →  якщо все добре: зберігаємо, redirect()->with('success', ...)

Метод контролера:

public function store(Request $request): RedirectResponse
{
    $validated = $request->validate([
        'name' => ['required', 'string', 'min:3', 'max:255'],
        'sku' => ['required', 'string', 'max:64', 'unique:products,sku'],
        'price' => ['required', 'numeric', 'min:0'],
        'category_id' => ['required', 'integer', 'exists:categories,id'],
    ]);

Product::create($validated);


return redirect()
        -&gt;route(&#039;shop.index&#039;)
        -&gt;with(&#039;success&#039;, &#039;Товар успішно створено!&#039;);
}</code></pre>


Ланцюжок помилок:


    

      

    • $request->validate() при невдачі кидає ValidationException;
      • 

    • Laravel перехоплює її і робить редірект назад (HTTP_REFERER), а помилки кладеться в спеціальний масив сесії;
      • 

    • наступний запит подання бачить змінну $errors (об'єкт ViewErrorBag) — глобально доступну в будь-якому Blade-шаблоні;
      • 

    • компонент директивою @error('name') показує текст помилки конкретного поля, клас is-invalid підсвічує рамку;
      • 

    • хелпер old('name', $default) витягує попередньо введене значення, щоб користувач не набирав форму заново.
      • 

    


Унікальність при редагуванні — окремий нюанс: правило Rule::unique('products', 'sku')->ignore($product->id) каже валідатору не рахувати власний поточний запис конфліктом.

09Eager Loading у поданнях

Подання каталогу виводить назву категорії для кожного товару. Без підготовки це проблема N+1: 1 запит на список + N запитів на категорії. Рішення — жадібне завантаження з лаб. 6: 
$products = Product::query()
    ->with(['category:id,name', 'reviews:id,product_id,rating,text'])
    ->orderBy('id', 'desc')
    ->paginate(10);

return view(&#039;shop.index&#039;, [&#039;products&#039; =&gt; $products]);</code></pre>

Тепер список каталогу — рівно 2–3 запити: сторінка товарів, сторінка категорій (по IN (...)), лічильник пагінації. Конструкція {{ $product->category->name ?? 'Немає' }} не виконує жодного запиту — дані вже в пам'яті. Оператор ?? 'Немає' страхує випадок, коли зв'язок відсутній.

10Feature-тестування інтерфейсу

Feature-тести перевіряють SSR-сторінки як HTTP-запити: дамо запит, отримаємо HTML, перевіримо зміст.

public function test_index_page_displays_entities(): void
{
    $product = Product::factory()->create(['name' => 'Унікальний Тестовий Товар']);

$this-&gt;get(&#039;/shop&#039;)
        -&gt;assertStatus(200)
        -&gt;assertSee(&#039;Унікальний Тестовий Товар&#039;)
        -&gt;assertSee(&#039;Додати новий запис&#039;);
}


public function test_create_form_validates_input(): void
{
    $this-&gt;post(&#039;/shop&#039;, [&#039;name&#039; =&gt; &#039;&#039;, &#039;price&#039; =&gt; &#039;invalid&#039;])
        -&gt;assertSessionHasErrors([&#039;name&#039;, &#039;price&#039;]);
}</code></pre>


Нюанси:


    

      

    • RefreshDatabase — кожен тест працює з чистою БД (SQLite у пам'яті);
      • 

    • фабрики з лаб. 6 створюють тестові дані за один рядок;
      • 

    • assertSee($value, false) — для перевірки сирого HTML (type="checkbox", name="customer_id"), бо за замовчуванням assertSee екранує та шукає екранований текст;
      • 

    • форма редагування замовлення тестується на наявність select покупця (name="customer_id") та чекбоксів знижок — так UI зв'язків 1:M/M:M стає контрактом.

12Як усе складається в лаб. 7

Архітектура додатку після лаб. 7:

├── API (лаб. 5–6, не змінено): /products, /catalog, /orders, ...  → JsonResponse
└── Web (лаб. 7)
    ├── /shop                → Web\ProductController   → shop/{index,show,create,edit}
    └── /manage/*            → Web\{Category,Customer,Discount,Order,Review}Controller
        └── manage/{...}/{index,create,edit}
views/
├── layouts/app.blade.php    — каркас, navbar, flash
├── components/form/input.blade.php — поле вводу з old() і @error
└── shop/, manage/, home     — 20 подань

Головна сутність Product отримала повний CRUD через HTML-форми, решта сутностей — масштабування того ж підходу. Зв&#039;язки з лаб. 6 (1:M, M:M) вперше працюють не через API, а через звичайні елементи HTML: select і чекбокси.

13Глосарій

    • SSR (Server-Side Rendering) — рендеринг HTML на сервері за кожен запит.
    • SPA (Single Page Application) — застосунок, що рендериться в браузері через JS на базі JSON API.
    • Blade — шаблонізатор Laravel (.blade.php), компілюється в PHP і кешується.
    • Директива — конструкція Blade на кшталт @if, @foreach, @csrf.
    • Макет (layout) — базовий шаблон зі спільним каркасом; успадковується через @extends.
    • @yield / @section — «мітка вставки» в макеті та заповнення її в дочірньому шаблоні.
    • Компонент — перевикористовуваний блок Blade; анонімні лежать у resources/views/components, виклик — <x-...>.
    • $slot — вміст між тегами компонента.
    • Flash-повідомлення — значення в сесії «на один наступний запит» (with('success', ...) → session('success')).
    • Method Spoofing — підміна HTTP-методу через приховане поле _method.
    • CSRF-токен — секрет сесії, що підтверджує автентичність запиту (@csrf, поле _token).
    • old() — хелпер, який повертає попередньо введене значення поля після невдалої валідації.
    • $errors — об'єкт з помилками валідації, доступний у всіх поданнях.
    • N+1 — антипатерн запитів, лікується жадібним завантаженням with().

14Питання для самоконтролю

    • У чому архітектурна відмінність SSR (Blade) від рендерингу на клієнті (SPA + JSON API)?
    • Яке призначення директив @yield та @section?
    • Як Blade захищає від XSS при виводі через {{ }}?
    • Для чого компоненти <x-...> і як працює $slot?
    • Що таке CSRF-атака і як @csrf захищає форми?
    • Навіщо Method Spoofing (@method('PUT')/@method('DELETE'))?
    • Який життєвий цикл помилок валідації — від validate() до $errors у Blade?
    • Для чого хелпер old()?

15Відповіді

    • SSR збирає готовий HTML на сервері за кожен запит; клієнт лише показує його. SPA отримує JSON і будує DOM у браузері. SSR простіший у захисті та краще віддає перший рендер; SPA — інтерактивніший після завантаження, але вимагає окремого API, клієнтської маршрутизації й стеження за станом.
    • @yield('content') у макеті оголошує місце вставки (з опціональним значенням за замовчуванням); @section('content') ... @endsection у дочірньому шаблоні надає вміст. @extends зв'язує шаблон із макетом.
    • {{ $var }} компілюється в htmlspecialchars($var, ENT_QUOTES), тож <script> стає &lt;script&gt; і не виконається. Сирої вивід — свідома дія через {!! !!}.
    • Компоненти інкапсулюють HTML-блок із пропсами (@props) та атрибутами ($attributes), усуваючи дублювання. $slot містить усе, що написано між відкриваючим і закриваючим тегами <x-...>.
    • CSRF-атака змушує браузер залогіненого користувача відправити запит без його відома. Токен з сесії (@csrf → поле _token) перевіряється middleware; запит без коректного токена отримує 419 і не доходить до контролера.
    • HTML-форми знають лише GET/POST, а REST вимагає PUT/PATCH/DELETE. @method('PUT') додає приховане поле _method=PUT, за яким маршрутизатор викликає потрібний метод контролера.
    • validate() при невдачі кидає ValidationException → Laravel редіректить назад і кладе помилки в сесію → наступний рендер має глобальну $errors → @error('field') показує текст, old('field') відновлює введене.
    • old('field', $default) читає «старе» значення поля з сесії після невдалого POST — користувач бачить свою форму майже незміненою, виправляє лише помилкові поля.
